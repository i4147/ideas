# 09 — `help2docs` (documentation from `--help`, for tools you don't own)

> **Difficulty 2/10** · **Effort ~2 days** · **Tier: warm-up**
> **Prior art: ❌ already built for your own tools** — `sphinx-click`, `mkdocs-click`, `click-man`, Typer's built-in `--help` docs, `argparse-manpage`, `help2man` (Perl).
> **Pivot required?** Yes — the whole framing has to change. Everyone who owns the source can already generate docs. **Nobody can document a CLI they only have a binary for.**

## The problem

You write internal docs/wikis/runbooks for tools you don't control: `kubectl`, `aws`, `terraform`, a vendor's CLI, a Go binary someone left. `--help` output is the only spec, and hand-transcribing 40 subcommands into Markdown is a week nobody wants to spend.

## What exists

| Tool | Requires |
|---|---|
| `sphinx-click` / `mkdocs-click` | your Click/Typer source |
| `argparse-manpage` | your `argparse` parser object |
| `help2man` | Perl, man pages only, flat (no subcommand tree) |
| `click-man` | your Click app |

All of them are *introspection* tools. The gap is a **black-box parser**: run `tool --help`, `tool sub --help`, recursively, and turn the text into a tree.

## The pivot, precisely

```
help2docs build kubectl --out docs/kubectl/ \
  --max-depth 3 --concurrency 4 --format md --index
help2docs build ./dist/mycli --skip 'completion|debug' --format man
help2docs diff docs/kubectl/ --against kubectl@v1.29   # catch vendor CLI drift
```

Parsing `--help` reliably means handling the three dialects that cover ~95 % of CLIs:

1. **argparse style**: `usage:`, `positional arguments:`, `options:` blocks with 2-space continuation indents.
2. **Click/Typer style**: `Usage:`, `Options:` with `-h, --help  Show this message…` and wrapped lines.
3. **cobra/Go style**: `Available Commands:`, `Flags:` with `--flag type   desc`, plus `Global Flags:`.

Implementation: a small hand-written block splitter (not a grammar) + regex extraction of `-s, --long [VALUE]`, then a fallback "verbatim" mode that keeps the raw text in a fenced block when parsing confidence is low. Never hallucinate structure: if a section can't be parsed, keep it verbatim and mark it.

**Subcommand discovery** is the clever part: extract candidate tokens from `Available Commands:`/`Commands:` sections *and* from `usage:` lines (`tool [command]`), then verify each by executing `tool <cmd> --help` and checking exit code 0 with non-empty output. Cache by `(binary mtime, args)`; run with `--timeout 5` and a per-command env `NO_COLOR=1 COLUMNS=120`.

## Output

`index.md` + one file per command, each with: synopsis, description, arguments table, flags table, inherited/global flags, examples section if present in help, and `<!-- generated by help2docs at vX -->`. Plus a `--format man` renderer (roff escaping: quotes, `.`, leading spaces).

`diff` mode compares the generated tree against a pinned baseline JSON → catches "the vendor renamed `--namespace` to `-n`" in CI.

## Build

```
help2docs/
  probe.py     # execute --help, env sanitization, timeouts
  dialects.py  # argparse / click / cobra parsers -> Section model
  tree.py      # subcommand discovery + verification + cycle guard
  render_md.py, render_man.py
  diff.py
```

**Safety**: executing a binary is a real risk. Only run with `--help`/`-h`, never a bare invocation; refuse if the binary isn't executable; print every command it intends to run under `--dry-run` first; support `--no-exec` with a static parse of saved help files (`--from-dir`).

## Tests

Golden files: capture `--help` output from a dozen real tools (kubectl, gh, pipx, ruff, docker, a Typer app, an argparse app, a cobra app) into `tests/fixtures/`, then assert the parsed model matches snapshots. Add a fake binary script in `tmp_path` that emits each dialect and exits 0.

## Pitfalls

- Help text wraps at terminal width → always set `COLUMNS` and `NO_COLOR`, strip ANSI.
- Some CLIs page output or require a TTY; use `subprocess` with `stdin=DEVNULL` and no pty by default.
- Subcommand explosion (`aws` has ~300) → depth limit + `--only` filters, and write incrementally.
- Keep the raw help text in a `<details>` block per page: it's the ground truth when parsing fails.

## Definition of done

`help2docs build kubectl --max-depth 2` produces a navigable Markdown tree in <60 s, with every page containing real synopsis/flags, and no invented content.
